Java Interview Preparation Notes

Section 1: HashMap Internals
A HashMap in Java stores key-value pairs in an array of buckets. When a key is inserted, its hashCode() is computed and then spread using a bitwise XOR of the high and low 16 bits, which reduces collisions when the table is small. The bucket index is calculated as (n - 1) & hash, where n is the table size, which is always a power of two. The default initial capacity is 16 and the default load factor is 0.75. When the number of entries exceeds capacity multiplied by load factor, the map resizes by doubling its capacity. With default settings, the first resize happens when the 13th entry is added, because 16 x 0.75 = 12. During resizing, every entry is redistributed, and each entry either stays at its original index or moves to index plus old capacity.

Section 2: Treeification in HashMap
Since Java 8, when a single bucket holds more than 8 entries and the table capacity is at least 64, the linked list in that bucket is converted into a red-black tree. This improves worst-case lookup from O(n) to O(log n). If the table capacity is below 64, the map resizes instead of treeifying. When a tree bucket shrinks to 6 or fewer entries during a resize, it is converted back into a linked list. This protects against performance degradation caused by many keys with colliding hash codes.

Section 3: The equals and hashCode Contract
If two objects are equal according to equals(), they must return the same hashCode(). The reverse is not required: two unequal objects may share a hash code, which is called a collision. If you override equals() without overriding hashCode(), objects that are logically equal may land in different buckets, and HashMap or HashSet will fail to find them. A good equals() implementation must be reflexive, symmetric, transitive, consistent, and must return false when compared with null. Fields used in hashCode() should be immutable while the object is stored in a hash-based collection, otherwise the object can become unreachable inside the map.

Section 4: ConcurrentModificationException
ConcurrentModificationException is thrown when a collection is structurally modified while it is being iterated, outside of the iterator's own methods. ArrayList and HashMap use a field called modCount to track structural changes. The iterator records the expected modCount when it is created and checks it on every call to next(). If the values differ, the iterator fails fast and throws the exception. The exception can occur in a single thread, for example when calling list.remove() inside a for-each loop. The safe alternatives are using iterator.remove(), using removeIf(), or using concurrent collections such as CopyOnWriteArrayList or ConcurrentHashMap, whose iterators are weakly consistent and do not throw this exception.

Section 5: ConcurrentHashMap
ConcurrentHashMap allows concurrent reads without locking and concurrent writes with fine-grained locking. In Java 8 and later, it no longer uses segments. Instead, it uses CAS (compare-and-swap) operations to insert into empty buckets and synchronizes on the first node of a bucket when that bucket already has entries. ConcurrentHashMap does not allow null keys or null values, because a null return from get() would be ambiguous in a concurrent context: it could mean the key is absent or that it maps to null. Methods such as computeIfAbsent() and merge() perform atomic compound operations.

Section 6: Java 21 Virtual Threads
Virtual threads were finalized in Java 21 as part of Project Loom. They are lightweight threads managed by the JVM rather than the operating system. Many virtual threads are multiplexed onto a small pool of platform threads called carrier threads. When a virtual thread performs blocking I/O, it is unmounted from its carrier thread, which is then free to run another virtual thread. This makes the simple thread-per-request model scale to very large numbers of concurrent tasks. Virtual threads are created with Thread.ofVirtual().start() or Executors.newVirtualThreadPerTaskExecutor(). They should not be pooled. A known limitation in Java 21 is pinning: a virtual thread inside a synchronized block that blocks cannot be unmounted, which ties up the carrier thread. Using ReentrantLock instead of synchronized avoids this in Java 21.

Section 7: Spring Bean Scopes
Spring supports several bean scopes. Singleton is the default: one instance per Spring container. Prototype creates a new instance every time the bean is requested. In web applications, request scope creates one instance per HTTP request, session scope creates one per HTTP session, and application scope creates one per ServletContext. When a prototype bean is injected into a singleton, it is injected only once, so the singleton always holds the same prototype instance. To get a fresh instance each time, use ObjectProvider, a lookup method, or a scoped proxy.

Section 8: Spring Transactions
The @Transactional annotation in Spring works through proxies. Because of this, calling a @Transactional method from another method in the same class bypasses the proxy, and no transaction is started. This is called the self-invocation problem. By default, Spring rolls back a transaction only for unchecked exceptions (RuntimeException and Error), not for checked exceptions, unless rollbackFor is specified. The default propagation is REQUIRED, which joins an existing transaction or creates a new one. REQUIRES_NEW always suspends the current transaction and starts a new one, which is useful for audit logging that must be saved even if the main transaction fails.

Section 9: Garbage Collection Basics
The JVM heap is divided into a young generation and an old generation. New objects are allocated in the Eden space of the young generation. Objects that survive minor garbage collections are moved to survivor spaces and eventually promoted to the old generation. G1 is the default garbage collector since Java 9. It divides the heap into equal-sized regions and prioritizes collecting the regions with the most garbage first, which is where its name comes from. ZGC is a low-latency collector designed to keep pause times under a millisecond, and in Java 21 it gained a generational mode enabled with the flag -XX:+ZGenerational.

Section 10: String Immutability and the String Pool
Strings in Java are immutable. Once created, their value cannot change. String literals are stored in the string pool, so two identical literals refer to the same object. Using new String("hello") creates a separate object on the heap, even if the same literal exists in the pool. The intern() method returns the pooled version of a string. Immutability makes strings safe to share across threads, safe to use as HashMap keys, and allows their hash code to be cached after the first calculation. For repeated concatenation inside loops, StringBuilder should be used because it avoids creating many intermediate string objects.
